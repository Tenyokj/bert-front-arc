The default is a **read-only preflight**, with no signer or dotenv loading in
the Node entry point. It refreshes the bounded historical inventory itself,
pins a single canonical block, verifies the old implementation/runtime, manifest
wiring, upgrade owner/admin role, module roles, four Factory generations,
balances, known donor/bond entries, 112 ordinary pool slots and the Initializable/
ReentrancyGuard namespaces. The compiler storage layout must preserve all old
fields and consume exactly ten reserved slots. Changed compiled sources fail.

This is deliberately limited to the currently reviewed pre-round history.
Opened funding rounds, unfamiliar financial events or explorer/RPC failures stop
the rollout rather than silently claiming a complete audit. Explorer discovery
is not an independently exhaustive chain scan. A future populated release needs
a broader inventory, not a bypass flag. Existing evidence is never overwritten.

## Explicit Public Phases

**The following commands send public Arc Testnet transactions.** They are not
permission for an agent to execute them. The configured Hardhat signer must be
the verified ProxyAdmin owner and protocol admin. Never paste its key into chat.
Run one phase, inspect its output, then proceed. No automatic all-phases mode.
Keep `ARC_TESTNET_RPC_URL` and `V24_EVIDENCE` from the preceding shell.

```bash
V24_PHASE=deploy-implementation V24_SEND=I_UNDERSTAND_PUBLIC_TRANSACTIONS \
npx hardhat run scripts/deploy/rollout-v2-4.ts --network arcTestnet

V24_PHASE=pause V24_SEND=I_UNDERSTAND_PUBLIC_TRANSACTIONS \
npx hardhat run scripts/deploy/rollout-v2-4.ts --network arcTestnet

V24_PHASE=upgrade V24_SEND=I_UNDERSTAND_PUBLIC_TRANSACTIONS \
npx hardhat run scripts/deploy/rollout-v2-4.ts --network arcTestnet

V24_PHASE=deploy-treasury V24_SEND=I_UNDERSTAND_PUBLIC_TRANSACTIONS \
npx hardhat run scripts/deploy/rollout-v2-4.ts --network arcTestnet

V24_PHASE=verify node scripts/deploy/rollout-v2-4.mjs

V24_PHASE=unpause V24_SEND=I_UNDERSTAND_PUBLIC_TRANSACTIONS \
npx hardhat run scripts/deploy/rollout-v2-4.ts --network arcTestnet
```

Implementation deployment happens before maintenance, to avoid pausing before
the implementation can be paid for and verified. Pause affects the existing
pool, VotingSystem and GrantManager only. Upgrade requires all three paused,
uses empty `upgradeAndCall` calldata, then compares pre/post storage, namespaces,
balances, references and Factory approvals. No initializer/reinitializer is run.
Revenue asset/receiver/share/pending policy/entitlements must all remain zero.

Treasury constructor is exactly the reviewed pool, USDC and immutable beneficiary
split from `release-config/arc-testnet-v2.4.json`: the selected address has 100%
of Treasury receipts, **not of pool custody**. Runtime bytes outside compiler-
declared immutable ranges, getters, every payee/share and creation calldata are
checked. The journal records actual addresses and canonical receipts, never
predictions as evidence. Unpause restores the original module pause states only
after upgrade and Treasury postchecks. The tool does not collect/pay revenue.

## Recovery and Staleness

Every send records intent and explicit nonce to disk first, then its hash and
canonical receipt. Pending signer transactions or insufficient estimated gas
coverage stop the next send. Gas is paid in native test USDC, not pool custody.
Repeated phases check their recorded transaction; they never silently resend it.
If an upgrade mined before its response was persisted, repeat the upgrade phase
to recover its recorded receipt and run postchecks, not to upgrade again.

If no hash was returned, inspect the wallet/explorer for that exact signer and
nonce, then set `V24_RECOVERY_TX` to the actual hash when repeating the same phase.
From/to/calldata/value/nonce/chain must all match the recorded intent. A missing
hash is **not** permission to use a fresh journal and send again. A reverted or
reorganized receipt stops for review. There is no automatic rollback.

The original block is rechecked for canonicality on every phase; confirmed
receipts are also rechecked. New pre-upgrade sends require a checkpoint no older
than one hour and unchanged captured state. If this expires **after any send**,
keep the journal and seek a reviewed recovery; do not delete/refresh it blindly.
An abandoned `.lock` after process death requires checking that the old process
has stopped before removing only that lock file. Never delete the journal.
