# Open V3.2 Finding: Correction Deadline and Stalled Cooldown

Date: 25 October 2026. Status: **fixed in new V3.2.1 infrastructure (Manager 2.0.1); historical immutable Managers remain affected**. This is an
internal liveness/business-logic finding, not evidence of stolen funds or an audit.

## Affected Behavior

In released Manager 2.0.0, `CommunityMilestoneManager.reopenAfterCorrection` resets the rejected review
tallies but retains the original `plan.proofDeadline`. `submitMilestoneProof`
still requires the current Community time to be at or before that deadline.

With the frontend's production defaults (14-day review, 7-day proof window),
even immediately submitted evidence finishes review after the original proof
deadline. A first rejection followed by the 48-hour cooldown allows reopening
but not submitting the corrected proof: the call reverts with `invalid proof`.
The accelerated demo's 5-minute proof / 1-day review configuration also exposes
this. Larger proof windows only mitigate early submissions; a first proof
submitted near its deadline can still hit the same defect.

There is a second liveness consequence: `failExpiredPlan` accepts only
`AwaitingProof`, not `CorrectionCooldown`. Only the execution recipient can
reopen correction. An absent recipient can therefore leave unpaid capital and
supporter obligations unresolved indefinitely in cooldown. This is distinct
from the bounded seven-active-day expiry of a payment authorization.

## Evidence

- The new local browser scenario successfully paid the initial 20%, rejected
  proof with three independent supporters, waited the 48-hour cooldown and
  reopened correction. Submitting corrected proof then failed.
- Before remediation, an explicitly named characterization in
  `test/V3/CommunityMilestoneManager.fully.ts` passed with 14-day review / 7-day
  proof terms, documenting the unchanged deadline and inaccessible cooldown expiry.
  It has now been replaced by a positive regression: corrected proof is accepted
  through the renewed fixed deadline. Four additional cases cover both milestones
  and expiry with or without an executor reopening the correction.
- Run: `npx hardhat test test/V3/CommunityMilestoneManager.fully.ts`.
  Result after source remediation: 16 passing. Full core suite: 237 passing.
- Expanded browser verification against a fresh local patched bundle passed:
  163 V3 UI receipts, including corrected-proof rejection/refunds and permissionless
  expiry of a paused/resumed abandoned stage-two correction. The combined V2/V3
  run passed in 3.3 minutes (223 UI receipts total, plus 44 read-only rejection checks).

The expanded frontend E2E uses the original accelerated demo's 5-minute proof /
1-day review settings. Local Community deployments use the patched artifact,
not the currently deployed Arc Manager. These scopes must not be conflated.

## Source Remediation, Not Yet Deployed

1. On the first rejected review, set a fixed correction deadline equal to the
   rejection finalization time + cooldown + the configured proof duration.
2. Reopening must not extend that deadline; late reopening must fail. Otherwise
   a vanished executor can still defer expiry by delaying the reopen action.
3. Permit anyone to expire an overdue plan from either `CorrectionCooldown` or
   `AwaitingProof`, preserving already-paid amounts and refunding only the
   unpaid execution budget.
4. Test late original proof, both milestones, 20%/60% already paid, absent
   executor, exact deadline boundaries, pause/resume and a single correction.
5. Align frontend and indexer deadlines with the corrected state transition.

## Release Consequence

No deployed contract has been changed. This finding remains open on existing
Managers even after local source tests pass. Existing Community
Managers are immutable; a source patch, frontend redeploy or Factory proxy
upgrade cannot silently change their behavior. A corrected bundle and explicit
new-Community deployment/migration policy must be followed before publishing a fix.
Do not use real funds for affected pilots.
