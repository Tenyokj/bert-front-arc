# V3.2: Release Preparation and Factory Identity

**Protocol release: V3.2 (unreleased). V2 remains V2.3.**

Status: **local implementation, not deployed**, 24 October 2026. This runbook
does not replace the existing Arc deployment record or authorize a deployment.
See [payment policy](V3.2-TRANCHE-QUORUM.md) and [security review](SECURITY-REVIEW-V3.1.md).

## Why a new Factory

The current CommunityFactory is not known to be broken. It stores initialized
Treasury/module-deployer references and exposes no setters to replace them.
A new Hub artifact using that old Factory would still create old modules.
An infrastructure proxy upgrade would not replace existing immutable Hubs or
Managers either. This rollout uses a fresh matching infrastructure bundle rather
than a silent proxy upgrade or an unreviewed new setter.

The original modular V3.1 Factory remains
`0xe16Cd61a21feA97393e6eEE3A7F7A26828021dD0`, from block `66809847`.
Original Communities retain their payout policy and known self-review limitation.
Do not describe them as patched. V3.0 is a separate historical monolithic layer;
its events are not compatible with the modular V3.1 graph templates.

## Identity and compatibility

Identity is `(chainId, factoryAddress, communityId)`. Every Factory has its own
counter, so both original and new Factory can contain Community #1.

- Frontend canonical URLs use `/v3/communities/<factory-address>-<id>`, including
  nested proposal and round links. Factory addresses must be configured/trusted.
- Numeric Arc bookmarks remain pinned to the original modular V3.1 Factory.
  They do not change target when `NEXT_PUBLIC_V3_FACTORY_ADDRESS` changes.
- On local Hardhat, numeric URLs use the configured local Factory, never Arc.
- Directory and profile read original plus configured Factories, keyed by Factory
  and ID; metadata queries filter by both. Discovery windows remain bounded:
  newest directory entries and newest 100 Communities per Factory for profile.
- The source frontend blocks creation with the known original Factory and new
  Hub artifact. Deploy matching new infrastructure before publishing that UI.
- The V3 graph keeps original Factory history and adds a static source for each
  new modular Factory. Existing factory-prefixed entity IDs avoid collisions.

## Before any release transaction

1. Review the payment/refund/role-nonce diff and remaining Slither findings.
2. Run Core tests and size checks from the pinned release commit. Run frontend
   lint/build, `npm run test:community-routing`, V3 graph codegen/build and docs
   synchronization. A Next build with ignored type errors is not a clean typecheck.
3. Commit and merge the coordinated Core/frontend/docs changes through PRs.
4. Preserve the current deployment manifest and rollback env/endpoint values.
   Do not replace production addresses with a local test deployment.

Verification in this preparation step: twenty-two frontend regression tests passed
(routing, decoding/build guards, pinned creation context and mapping state tests),
frontend lint/build and two-Factory graph codegen/build passed. The generated
graph manifest was then rebuilt with the original real Factory only, removing
dummy build-test addresses. Docs have 45 unique slugs with no broken internal
links. Whitepaper 1.3.0 was regenerated and its changed pages visually inspected.
**Frontend type checking is now enforced:** `npm run typecheck` passes;
`ignoreBuildErrors` was removed. Graph AssemblyScript is excluded from the Next
TypeScript project and checked through its own codegen/build pipeline. Manual dApp E2E and
live graph replay were not performed in this step.

No V2 implementation upgrade, legacy-retirement rerun, or allowlist reinitializer
is required merely to add this new V3 Factory to the already migrated FundingPool.
Do not pause or upgrade eight V2 contracts as an incidental documentation step.

## Deployment order

1. Run `scripts/deploy/deploy-v3-2.ts --network arcTestnet` using the intended
   PoPVerifier and explicit ProxyAdmin owner. It deploys the matching library,
   Treasury/module deployers and Factory implementation/proxy. Record all output,
   transaction receipts and real Factory deployment block. No new addresses are
   assigned in this runbook.
2. Verify the deployed source/build and initialized dependency addresses. Use
   `scripts/deploy/configure-v3-2-funding-pool.ts` with the existing FundingPool
   and **new** Factory. It adds approval without removing previous Factories.
   Confirm old approvals remain true as well as the new one.
3. Build the V3 graph with the new `V3_FACTORY_ADDRESS` and
   `V3_FACTORY_START_BLOCK`. The manifest generator automatically retains the
   original modular V3.1 Factory at block 66809847. `V3_FACTORY_SOURCES` optionally
   accepts a JSON array of further `{address,startBlock}` sources. Never publish
   a manifest generated with dummy test addresses.
4. Deploy an unused version label to the existing Studio slug
   **`bert-v-3-1-arc-testnet`**. V2's subgraph is separate and is not replaced.
   Wait for sync, inspect indexing errors and query both Factory identities.
   Build/codegen success alone is not a deployed or synced graph.
5. Record receipt-backed new addresses and endpoint/version in manifests and docs
   as an additional generation; preserve the original Factory record. Set Vercel
   `NEXT_PUBLIC_V3_FACTORY_ADDRESS` and matching Admin-actions library to the new
   bundle, and `NEXT_PUBLIC_V3_SUBGRAPH_URL` to the synced version. Keep
   `NEXT_PUBLIC_V3_EVENT_FROM_BLOCK=66809847` for retained Community history.
   Additional old modular Factories can be configured using comma-separated
   `NEXT_PUBLIC_V3_LEGACY_FACTORY_ADDRESSES`.
6. Redeploy the frontend only with that matching env. Publish docs and the
   whitepaper revision; change source-only labels only after verified evidence.

## Smoke checks and remaining assurance

- Open the same local Community ID under both original and new Factory URLs;
  check distinct Hub/Treasury/modules. Old numeric bookmarks must remain old.
- Check legacy communities still load with legacy payout warnings; opening them
  does not apply new policy. Unknown Factory URLs must not yield writable targets.
- Create a new Community through the new Factory and verify actual Manager code
  and current-role nonce views. Settlement must reserve, not auto-pay the 20%.
- Check all new tranche events and current approval reads. Only actual Paid events
  increase released amounts in the new Manager; historical approvals are not an
  authoritative current quorum. Old automatic-release events remain indexed.
- Confirm V2 read/write paths and both old/new reserve authorizations still work.

These smoke checks do not replace the four-lane manual dApp E2E, adversarial
testing or independent security audit. Deployment safety and responding to tester
findings remain the maintainer's responsibility, not something delegated away.

Before staging/pushing, use the [pre-PR review and handoff](V3.2-PRE-PR-REVIEW.md).
