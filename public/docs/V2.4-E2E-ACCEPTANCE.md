## Reproduction

From the sibling frontend checkout, with its dependencies installed and core
artifacts compiled:

```bash
npm run test:e2e:revenue
npm run test:e2e:all
```

The first command exercises V2.4; the second also repeats the existing four-lane
V3.2.1 browser regression with the candidate FundingPool. The owned node uses
`127.0.0.1:18545`, chain 31337, eight public development accounts and MockUSDC.
The dApp is a production build on `127.0.0.1:13000`; occupied ports abort setup.
Personal `.env` files, public deployments and normal `.next` output are not
replaced. Queue fillers and pause/unpause are direct fixture transactions;
target proposals, plans, votes, reviews, payments and refunds use the browser.

The injected EIP-1193 provider is explicitly a **test wallet**, not the MetaMask
extension, an identity provider or a replacement for public-RPC validation.
Its transaction transport rejects non-local networks. Time jumps satisfy only
local deadlines, never the public 48-hour notice or real review windows.

Local Treasury uses account 1 as a disposable beneficiary with a 10,000-bps
share. This does not replace the owner-selected public beneficiary recorded in
[release configuration](V2.4-RELEASE-CONFIGURATION.md). The fee share is the
selected 2,000 bps of eligible earned fees, not of pool custody.

## Observed Results

- Combined Chrome run: **2 tests passed, 3.9 minutes** of browser runtime,
  excluding local deployment and build. Separate revenue-only runs also passed.
- Revenue scenario: **106 confirmed UI transactions**, 34 separately labeled
  direct fixture receipts, four V2 rounds and 36 revenue-related event logs.
- A 30-USDC winning pledge total earns 1.5 USDC in fees on full execution:
  0.3 USDC Treasury and 1.2 USDC reserve. The failed grant earns only its initial
  0.3-USDC fee: 0.06 Treasury and 0.24 reserve; backers recover 24 USDC gross.
  Across these two revenue-enabled outcomes Treasury accrues/collects/pays
  **0.36 USDC**, or 360,000 six-decimal units, with zero remaining pool credit.
  The separate zero-revenue success and no-winner outcome create no revenue.
- The core full suite was repeated: **268 passing in 41 seconds**. The frontend
  root suite was repeated: **87 passing**. These counts are not a measure of
  audited paths or proof that every user flow is covered.
- Receipt replay initially exposed a decoder-harness omission for argumentless
  `RevenuePolicyCancelled`: Viem returns no `args`. The harness now decodes this
  as an empty parameter object. No Solidity or production mapping change was
  needed. Browser financial assertions found no unexplained differences.

Generated browser reports/logs live under frontend `.e2e-results/` (Git-ignored).
`revenue-browser-receipts.json` includes mined UI receipts, separately labeled
fixture receipts and raw revenue logs. The runner removes the old revenue file
before setup and runs mapping replay after browser success; a failed or terminated
run cannot be accepted by silently reusing the previous fixture.

## Graph Gate: Resolved on a Separate Fresh Chain

The [real Graph Node acceptance](V2.4-GRAPH-ACCEPTANCE.md) now passes discovery,
exact agreement with 38 RPC revenue logs, process restart, two-block reorg and

bounded Graph gate without mislabeling it as native-Arc or browser execution.
