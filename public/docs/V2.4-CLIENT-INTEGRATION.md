# V2.4 Client Integration Candidate

Updated 2026-11-24. Local branch `feat/v2-4-treasury-ui` exists in the dApp and
Console checkouts. No public upgrade, deployment, policy activation, commit or
merge was performed. V2.3 remains the deployed FundingPool version.

## Implemented

The clients share a mirrored Viem reader and accounting readout. Each snapshot
pins reads to one mined block, checks the chain, token decimals, accounting
invariants, Treasury pool/token bindings and fixed-beneficiary share totals.
Legacy pools retain base accounting; unsupported revenue is unavailable, not zero.
Transport errors or malformed new getters are never silently converted to legacy
success. Runtime selector detection is a compatibility hint, not code verification.

The dApp `/pool` supports current/scheduled settings and historical round lookup,
Admin-only scheduling/cancellation, delayed permissionless activation, Treasury
collection and release to fixed beneficiaries. Actions recheck wallet/chain and
Admin permission, simulate, lock duplicate clicks and inspect receipt status.
Ambiguous wallet responses block resending until an explicit accounting refresh.
No token approval, arbitrary beneficiary withdrawal, APY or investor share exists.
The old misleading donor "Share of pool" card is removed.

Console `/funding` adds a distinct RPC panel beside indexed funding data.
`/api/treasury` supports a bounded positive round ID and configured pool only;
it exposes no wallet, signing or write endpoint. Current/scheduled/selected-round
Treasuries expose at most 16 payees each. Arbitrary complete receiver history
and event-derived revenue timelines are separate indexer work, not claimed by
this RPC panel. A subsequent [local indexer candidate](V2.4-INDEXER-INTEGRATION.md)
now provides the event model; it has not been deployed or substituted for RPC.

## Client Dependency Patch - Verified Locally, Not Published

The earlier builds on Next.js 16.4.3 stopped at its security guard. On November 24,
Next.js and eslint-config-next were pinned to 16.4.6 in both clients, including
lockfiles and installation. Both production builds now pass without bypassing
the guard. Reader tests, TypeScript, lint, compiled-contract checks and bounded
desktop/mobile browser smoke were repeated. RainbowKit/Wagmi were not migrated.
Console adds pinned Viem 2.57.11, matching the dApp, without changing contracts.

Next no longer appears in either audit. Console production-only audit is zero;
its full audit retains seven moderate development findings. The dApp audit is
not clean: 38 package-level findings (19 high/19 moderate), or 31 production-only
(19 high/12 moderate), including Zod 3 and other connector/transitive paths.
These remain open; see the frontend `DEPENDENCY-SECURITY.md` dated patch record.
Counts are advisory snapshots, not confirmed exploit counts. Public clients are
not patched until review, merge and deployment actually occur.

Local UI/integration evidence is prepared; it does not authorize public rollout
or close full acceptance and deployment in the [release checklist](V2.4-RELEASE-CHECKLIST.md).
Documentation/configuration was subsequently prepared locally, including the
owner-approved 20% eligible-fee share, immutable 100% beneficiary and 48-hour
notice. See the [configuration record](V2.4-RELEASE-CONFIGURATION.md); it is not
a public deployment or authority to broadcast transactions.

The subsequent [browser acceptance](V2.4-E2E-ACCEPTANCE.md) passes actual
GrantManager creation/pledge/20/40/40/refund flows and revenue settings/collection/
fixed payments. It records 106 UI receipts using a local test provider and
MockUSDC. The original readout smoke above remains a narrower historical check;
neither test is described as real MetaMask or complete native-Arc acceptance.
