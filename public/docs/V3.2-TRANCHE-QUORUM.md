# V3.2: Admin Quorum for Execution Tranches

**Protocol release: V3.2, deployed on Arc Testnet. V2 remains V2.3.**

**Status: deployed in the new V3.2 infrastructure on 24 October 2026.** See
[deployment evidence](V3.2-ARC-TESTNET-RELEASE.md). This is the agreed follow-up to
the self-review patch. It does not change existing immutable Arc Communities.
Manager `2.0.0` introduces a material change to the payment state machine;
this per-contract version does not announce a protocol-wide V2 or V3 release.

## Policy

Every winning Admin/Member Binary/Slate execution plan follows the same stages:

| Payment stage | Becomes ready | Amount | Next state after actual payment |
| --- | --- | --- | --- |
| 0 | Winner settlement | floor(20% of execution budget) | Await first proof |
| 1 | First proof passes supporter review | floor(40% of execution budget) | Await completion proof |
| 2 | Completion proof passes supporter review | Entire remaining amount, approximately 40% | Completed |

All funds remain in `milestoneReserveByPlan` until the actual transfer or a
terminal refund. Neither supporter proof approval nor an Admin approval moves
capital into free execution balance. Validator reward accounting is deducted
before the plan budget is formed and is untouched by payment authorization.

## Immutable authorization and timing

- Each plan/stage opens exactly once with a fixed amount, the Community's immutable
  execution recipient and existing `adminApprovalThreshold`.
- Every stage needs fresh explicit approvals. Proposal creation, earlier tranche
  approvals and supporter review votes do not count as payment approvals.
- Approval and actual transfer must both finish before `readyAt + 7 days` on
  `communityTime()`. No request cancellation/reopening can extend this window.
- Pause freezes that clock and prevents approval, execution and expiry writes.
  Seven active days are not a guarantee of seven wall-clock days or an escape
  from an indefinitely paused Community; Admin pause remains a trust assumption.
- At the exact deadline approvals/payments are rejected and permissionless expiry
  becomes available. No automatic payout bypass is introduced.
- After quorum, anyone can relay the transfer through Hub. Only the fixed
  amount/recipient are paid, so the relay cannot choose or receive the budget.
- A next proof deadline starts only after actual payment of the preceding tranche.
  An approved completion proof is not `Completed` until the final transfer occurs.

## Current Admin roles, not historical signature counts

Membership maintains `adminRoleNonce(address)`, incremented on both role removal
and appointment. A tranche approval records that nonce. Execution verifies the
wallet is still an Admin and its nonce still matches. Removing and readding an
Admin cannot revive an old approval; it must explicitly approve again.

The executor supplies a **strictly ascending** address list of exactly the quorum
size. Every listed address must have a valid approval for the current plan/stage.
Sorting prevents duplicates. Runtime work is bounded by the quorum size, not an
ever-growing historical roster. `getExecutionTrancheApprovers` is discovery data:
it includes wallets whose approval may since have become invalid and is not a
trusted onchain quorum count.

## Expiry and refunds

Any wallet may call expiry on an unpaid stage at/after its deadline, even if
approvals reached quorum but nobody executed payment. The plan fails and its
entire **not-actually-paid execution budget** becomes pro-rata pull-refundable:

| Already paid | Execution budget refunded |
| --- | --- |
| Nothing | 100% |
| Initial 20% | 80% |
| Initial 20% + first 40% | Remaining approximately 40% |

Integer rounding is resolved by the final tranche/final refund claimer. Paid
tranches are not clawed back. The separate validator reward reserve is not part
of this refund base. Financial supporter weights include a contributing execution
recipient; that address remains excluded from milestone review, quorum and
approver-count calculations. Refund claims and exit-lock clearing retain their
existing protections against double claims and premature exit.

## API

Users write only through CommunityHub:

```text
approveExecutionTranche(planId)                      current Admin only
executeExecutionTranche(planId, sortedApprovingAdmins) anyone, before deadline
expireExecutionTranche(planId)                       anyone, at/after deadline
```

Manager views:

```text
pendingTrancheByPlan(planId)
getExecutionTranche(planId, stage)
getExecutionTrancheApprovers(planId, stage)
hasExecutionTrancheApproval(planId, stage, admin)
```

`ExecutionPlanStatus.AwaitingTranche` is appended as value **7**, preserving the
old status numbers and plan tuple shape. `releasedAmount` tracks transfers only;
`proofDeadline` is zero while awaiting a payment. Missing pending state is not a
free withdrawal or a permission to bypass milestone review.

## Events and integrations

`ExecutionTrancheReady`, `ExecutionTrancheApproved`, `ExecutionTranchePaid` and
`ExecutionTrancheExpired` separate authorization from payment. In Manager 2.0.0,
`ExecutionPlanStarted.initialTranche` and `MilestoneApproved.releasedAmount` are
zero: those events no longer imply a transfer. The new Paid event increments the
indexed release total. Legacy events remain supported for original Managers.

Frontend includes fixed-payment controls, valid-current-approval checks, sorted
witness generation and active-time expiry/refund controls. V3 subgraph adds
tranche/approval entities; historical approvals must still be revalidated onchain.
ABIs and the deployable Hub artifact are synchronized locally. No live subgraph,
Vercel environment or deployment manifest is changed by this implementation.

## Versions and rollout

- Manager `2.0.0`: changed payment lifecycle and added authorizations.
- Hub `2.1.0`: thin payment routes and Admin role-nonce view.
- Membership `1.1.0`: additive per-Admin role-incarnation tracking.
- CommunityTypes `2.1.0`: appended status and payment-term struct.
- Membership/Milestone deployers `1.1.0`: updated embedded creation code.

A new Hub artifact alone does not select a patched Manager: the chosen Factory's
module-deployer references determine which modules it deploys. Rollout must use
matching reviewed deployers/Factory and explicitly handle original immutable
Communities. Do not label old Communities upgraded or replace addresses silently.
The [rollout runbook](V3.2-QUORUM-ROLLOUT.md) specifies Factory-aware frontend
identity, additive graph sources and the deploy/configure/index/publish sequence.
