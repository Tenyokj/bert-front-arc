## Release boundary

V3.1 is a new `CommunityFactory` deployment. It does not upgrade, replace, or
reinterpret V3.0 Communities. Existing V3.0 Factory, Hub, Treasury, and
Community state remain part of the historical testnet release.

Do not deploy V3.1 from an unreviewed local worktree. The release must use a
reviewed merge commit, a recorded contract build, and the addresses produced by
that exact build.

## Blocking prerequisite: Factory allowlist

The currently deployed `FundingPoolUpgradeable` stores one `communityFactory`
address. Calling `setCommunityFactory(v3_1Factory)` after V3.0 is live would
replace V3.0 authorization and break future protocol-reserve routing from V3.0
Community Treasuries.

Before V3.1 deployment, release and verify an additive Factory allowlist that:

1. preserves the legacy `communityFactory` read for compatibility;
2. permits reserve transfer only when the caller Treasury is active in at least
   one explicitly approved Factory;
3. lets the protocol Admin add or revoke a Factory deliberately;
4. emits an event for every allowlist change;
5. has regression tests proving V3.0 and V3.1 Treasury callers can both route
   their own reserve, while arbitrary callers and revoked Factories cannot.

Until this prerequisite is deployed and verified, do **not** run
`configure-v3-1-funding-pool.ts` on Arc Testnet.

## Upgrade and migrate FundingPool

Keep the V2 modules paused for the complete upgrade and migration window. The
FundingPool upgrade is append-only storage: it adds the Factory allowlist after
all existing V2.3 state and does not rewrite pledges, grants, donor balances,
or protocol reserve accounting.

```bash
# 1. Pause the V2 operational modules.
V2_MAINTENANCE_ACTION=pause \
npx hardhat run scripts/deploy/set-v2-maintenance-state.ts --network arcTestnet

# 2. Upgrade only the FundingPool proxy to the reviewed implementation.
PROXY=<funding_pool_proxy> \
IMPL=FundingPoolUpgradeable \
npx hardhat run scripts/deploy/upgrade-proxy.ts --network arcTestnet

# 3. Seed the allowlist from the existing V3.0 Factory. The script requires
#    FundingPool to remain paused and refuses a missing or code-less Factory.
FUNDING_POOL_ADDRESS=<funding_pool_proxy> \
npx hardhat run scripts/deploy/initialize-v3-factory-allowlist.ts --network arcTestnet
```

Before proceeding, read `communityFactory`,
`isCommunityFactoryApproved(legacyFactory)`, USDC balance, `totalPoolBalance`,
and `protocolReserve`. The legacy Factory must be approved and each accounting
value must match its pre-upgrade snapshot.

## Preflight

1. Run `npm test`, `npx hardhat compile`, coverage, and the documented Slither
   command from the reviewed Core commit.
2. Confirm the independent reviewer/tester report is attached to the release
   issue or pull request. No external audit is implied by this checklist.
3. Record current Arc Testnet addresses for V2 proxies, PoPVerifier, V3.0
   Factory, the V2 and V3 subgraphs, and frontend deployment.
4. Confirm the deployer and ProxyAdmin owners are the intended testnet
   operational accounts. Use a multisig for any future production path.
5. Verify `POP_VERIFIER_ADDRESS` has code and is the intended testnet verifier.
6. Confirm the selected USDC token, RPC, chain ID `5042002`, gas balance, and
   block explorer before submitting a transaction.

## Deploy V3.1 infrastructure

After the Factory allowlist prerequisite is live:

```bash
cd ~/bert/bert-core

POP_VERIFIER_ADDRESS=<arc_testnet_pop_verifier_proxy> \
V3_PROXY_ADMIN_OWNER=<v3_1_proxy_admin_owner> \
npx hardhat run scripts/deploy/deploy-v3-1.ts --network arcTestnet
```

Record all output values in the release manifest:

- deployment transaction hash and block;
- `CommunityFactory` proxy, implementation, and ProxyAdmin;
- `CommunityAdminActions` library;
- Treasury, Membership, Proposal, Voting, and Milestone module deployers;
- commit SHA and artifact build timestamp.

## Authorize V3.1 reserve routing

Run the additive Factory authorization script only after inspecting the old and
new Factory addresses onchain. It must add V3.1 without removing V3.0.

```bash
FUNDING_POOL_ADDRESS=<funding_pool_proxy> \
V3_1_FACTORY_ADDRESS=<v3_1_factory_proxy> \
npx hardhat run scripts/deploy/configure-v3-1-funding-pool.ts --network arcTestnet
```

Verify directly from chain:

1. V3.0 Factory remains approved.
2. V3.1 Factory is approved.
3. An unrelated address is not approved.
4. `FundingPool` still points to the expected USDC contract and is unpaused.

## Indexer and application release

1. Update the V3 subgraph manifest to the new Factory address and deployment
   block. V3.1 must have its own start block and must never index from genesis.
2. Generate types, build, deploy a versioned V3 subgraph, and wait for `Synced`.
3. Query the deployed V3 endpoint directly before setting frontend variables.
4. Set `NEXT_PUBLIC_V3_FACTORY_ADDRESS`,
   `NEXT_PUBLIC_V3_EVENT_FROM_BLOCK`, and the versioned V3 subgraph URL in the
   frontend environment.
5. Deploy the frontend from the matching reviewed frontend commit.
6. Update the public documentation address registry and changelog only after
   the transaction receipts and indexer endpoint are known.

## Arc Testnet smoke tests

Use fresh verified test wallets. Record every transaction hash.

1. Reserve a Treasury, deploy the matching Hub, and activate one V3.1 Community.
2. Confirm the Factory resolves the canonical Hub/Treasury/module addresses.
3. Join as a Member with exact USDC allowance, then check role-exclusivity and
   an invalid join path.
4. Execute one Admin Binary and one Member Binary flow through settlement.
5. Create a Slate round and confirm an ineligible proposal cannot be included.
6. For one winner, verify Treasury reserve, `20 / 40 / 40` release, winning
   supporter-only review, the 40% eligible support-weight quorum, 6,667 bps approval,
   and minimum distinct-approver threshold.
7. Run one failed-plan path and verify pull refunds are limited to the winner
   supporter snapshot and exactly the unreleased budget.
8. Exercise a two-Admin pause/resume or withdrawal cancellation request and
   verify active-time deadline handling.
9. Confirm direct contract reads agree with the V3 subgraph after it catches up.

## Release evidence and rollback posture

Publish a release manifest with every address, implementation, proxy admin,
deploy block, transaction hash, code commit, subgraph URL, and frontend URL.

There is no safe "undo" for a deployed Factory or Community. If a defect is
found, pause the affected Community through its quorum mechanism when possible,
disable affected frontend actions, preserve evidence, and prepare a reviewed
upgrade or a new isolated release. Do not overwrite historical addresses or
silently repoint an existing Community.
