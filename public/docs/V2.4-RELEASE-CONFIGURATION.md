# V2.4 Arc Testnet Release Configuration

Status: **owner-selected testnet terms; source candidate, not deployed**.
Updated 2026-11-24. This runbook is preparation, not permission to send a public
transaction. Public versions remain V2.3 + V3.2.1 until receipt-backed rollout.

## Approved Terms and Distinct Percentages

| Item | Selected for Arc Testnet |
| --- | --- |
| Policy notice | 48 hours / 172,800 seconds, approved November 24 |
| Treasury share of eligible earned fees | 20% / 2,000 bps, approved November 24 |
| Beneficiary | `0xA4B0a01dB1d68D4CDB007F78bAB63Cb4ebd814bF` |
| Beneficiary share of Treasury receipts | 100% / 10,000 bps, approved November 24 |
| New Treasury address | Not deployed; `null` until verified receipt/constructor evidence |
| Revenue immediately after pool upgrade | Zero receiver / zero share; no revenue initializer |

The percentage is not a share of all pool money. With the existing 5% fee, full
execution of 100 USDC of pledge-funded winning capital pays the author 95 USDC,
credits Treasury 1 USDC and retains 4 USDC as reserve. Paid stages vest fees
progressively. Existing rounds keep their policy; direct deposits, bonds,
refunds, grant principal, surplus, V3 inflows and reserve top-ups are not the
eligible team-revenue base. Exact integer rounding remains contractual.

The beneficiary is also the current testnet administrator. This is not a
multisig or mainnet custody arrangement. Use separately reviewed governance,
custody and operational controls before real-value deployment. No beneficiary
rotation/rescue exists for this immutable Treasury; lost/blocked funds may be
permanently inaccessible. New receiver policy cannot rewrite old entitlements.

## Machine-Readable Draft and Offline Check

`release-config/arc-testnet-v2.4.json` records the selected terms and **expected
previous** addresses from the existing manifest. It is not a second live manifest.
It records no new implementation/Treasury address or receipt before deployment.

```bash
node scripts/deploy/prepare-v2-4-release.mjs
node --test scripts/deploy/prepare-v2-4-release.test.mjs
```

The tool validates the target chain/proxy/old implementation/admin/token against
the local manifest, zero initial revenue, bounded unique payees, exact share sum,
approval flags, compiled ordinary FundingPool runtime size and code hash. It
uses no RPC, signer, secret or send method. An alternate draft path is the only
optional positional argument. Unknown fields, wrong targets, malformed splits
and nonzero automatic initial revenue fail closed.

`activationTermsComplete: true` means only that the selected fields are complete.
`treasuryAddressRecorded` means an address was entered, **not verified deployed**.
`readyToBroadcast` always remains false. Five offline tests pass. A full fresh
preflight and acceptance evidence are separate requirements.

## Controlled Sequence - Do Not Execute Before Acceptance and Authorization

### PR Handoff

The bounded local acceptance is recorded as complete in
[the acceptance matrix](V2.4-E2E-ACCEPTANCE.md). This does not authorize public
writes. Prepare four separately reviewed PRs; do not commit personal `.env`
files, `.DS_Store`, temporary Docker data or unrelated changes.

| Repository | Candidate branch | PR base | Publication order |
| --- | --- | --- | --- |
| Core | `feat/v2-4-revenue-accounting` | `arc-usdc-migration` | Review/merge source first; merging does not deploy contracts |
| Docs | `docs/v2-4-release-candidate` | `arc-docs-migration` | Review/merge candidate-labelled documentation; it must still say not deployed |
| Frontend + V2 subgraph | `feat/v2-4-treasury-ui` | `arc-front-migration` | Keep Draft until the controlled pool rollout is verified; merging can trigger Vercel |
| Console | `feat/v2-4-treasury-ui` | `arc-console-migration` | Keep Draft until the same publication checkpoint; merging can trigger Vercel |

The backend has no V2.4 feature changes to publish. V3 Factory/subgraph addresses
are unchanged. A GitHub PR, green preview or merge is not Graph Studio publication,
contract verification, a deployed Treasury address or policy activation.

After the core merge, update its default branch only from a clean worktree,
compile the reviewed source and capture the fresh pinned preflight. Do not pause,
upgrade or schedule revenue from these PR commands. The public execution and
receipt-recording commands are a separate reviewed checkpoint below.

### Public Rollout Checkpoints

1. Freeze reviewed source, compiler, lockfiles and exact artifact/runtime hash.
   Refresh the 307-byte EIP-170 headroom after any source/compiler change.
2. Complete the agreed wallet/GrantManager/Graph Node matrix, including failure,
   refunds, prior rounds, pause and V3 reserve routing. Do not promote store-double
   replay or direct authorized-module probes to complete E2E evidence.
3. Capture a fresh pinned inventory and authority/runtime snapshot. Compare all
   existing roles, references, balances, obligations, Factory approvals, proxy
   slots and upgrade authority. Historical block 73753950 is not a fresh preflight.
4. Obtain explicit public-write authorization. Under reviewed maintenance controls,
   pause the affected V2 modules, deploy and verify the FundingPool implementation,
   and upgrade the **existing pool proxy** via the verified ProxyAdmin with empty
   initializer calldata. There is no revenue reinitializer. Do not redeploy V2 or V3.
5. Verify storage/wiring/accounting and zero receiver/share before reopening.
   Deploy the immutable Treasury with the exact pool/token/payee/share tuple;
   verify runtime, constructor arguments and receipt. Record the real addresses
   in deployment evidence only after confirmation. Staging may reorder Treasury
   deployment before the upgrade, but must never infer it from a predicted address.
6. Publish reviewed dApp/Console/V2 Graph versions. Keep original Graph start blocks;
   compare indexed entities and RPC with known receipts and sync/error status.
7. Only after separate confirmation of the verified receiver and chosen terms,
   schedule `(treasury, 2000)`. Record the on-chain ready timestamp, wait the full
   48 hours, execute the exact proposal and verify the active policy. Test time
   jumps cannot satisfy this public wait; scheduling is not activation.
8. Run the controlled public pilot and record actual transactions, observations,
   limits and any remaining risks. Publish the release with those boundaries.

The generic `upgrade-proxy.ts` is not a complete V2.4 migration guard or evidence
collector: the operator must not treat a success string as the whole preflight.
The dedicated public execution/evidence workflow must be reviewed at rollout;
this offline planner is deliberately not a replacement transaction sender.

## Recovery and Release Evidence

An ambiguous wallet/RPC result is not proof of revert. Check canonical receipts
and on-chain postconditions before any resend; do not increase a nonce blindly.
Capture tx hash, block/hash, chain, old/new implementation, admin/owner, runtime
hash, constructor arguments, settings, accounting before/after and Graph _meta.

Before any accrual, an old implementation is still not an automatic safe rollback:
review the exact state and incident response. After scheduling/token pinning,
snapshots or credits, blindly downgrading is unsafe. Prefer pausing affected
operations and a reviewed forward fix. Collected Treasury funds remain governed
by their immutable split and issuer restrictions, not by a rescue switch.
